# Working on GRABNES (for coding agents and contributors)

GRABNES is research code maintained by physicists. A change must be readable by a physicist, checkable against
an equation, and must not change any existing result unless that result was wrong. Read this file before editing
anything. Details are in [`docs/development/coding-conventions.md`](docs/development/coding-conventions.md) and
[`docs/development/output-style.md`](docs/development/output-style.md); this file lists what matters most.

## Before you change code

- Look for an existing routine that already does the job (`lanczosKuboCode/Src/`, `tools/`) and reuse it or
  add an option to it. Implement a piece of physics once and call it from every place that needs it.
- Keep the change minimal. Do not reformat, rename or reorganise code you are not changing. `HamHopping`
  (`ham.F90`) is a large tree of model-specific branches: touch only the branch you need
  ([`hamhopping-restructuring.md`](docs/development/hamhopping-restructuring.md) is a separate, planned task).

## Rules for the change

1. **Existing results stay the same.** New behaviour goes behind a new input key whose default reproduces the
   previous result. A default changes only to replace a result that was wrong, and the run log says so.
2. **A model that cannot work stops** with `MIO_Kill` and a message that names the key and says what to do.
   Never continue with unset values. A key that has no effect in the selected calculation gives a warning.
3. **Input keys** have the form `Section.Name` (`Kubo.Epsilon`, `Diag.SparseUseShift`). The line that reads a key
   is followed by its description:
   ```fortran
   call MIO_InputParameter('Kubo.Epsilon',eps,0.01_dp)
     !! - `Kubo.Epsilon`: Recursion DOS: broadening eta of the continued fraction [eV].
   ```
   Energies in the input are in eV (read them with `HamInputEnergyEV` where it applies). Former key names keep
   working through `Src/MIO/input_aliases.inc`; never break an existing input file.
4. **Units and signs inside the solver:** energies are in units of the hopping `g0`; eV appear only in input and
   output. `hopp(j,i)` holds MINUS the hopping of neighbour `j` of atom `i`; anything new that uses it must carry
   the minus.
5. **Output** goes through `MIO_Print(message, 'module')`, never `print *` or `write(*,*)` outside `Src/MIO`.
   Memory through `MIO_Allocate`/`MIO_Deallocate`. `MIO_Allocate` zeroes an array only when it (re)allocates it:
   initialise explicitly what must start at zero.
6. **OpenMP:** every parallel loop lists its `PRIVATE` and `REDUCTION` variables; every scalar assigned inside the
   loop is private (Fortran's default is SHARED, and a missed one gives run-to-run differences). `in1`, `in2` are
   per-thread ranges: never use them as the bounds of an `!$OMP PARALLEL DO`.
7. **`#ifdef DEBUG` blocks are removed from the normal build.** Never put a statement that must run inside one
   (the `MIO_Debug` trace calls at the top of a routine sit in such a block).
8. **Layout:** three spaces per indentation level, no tabs, no trailing blanks, lines below 132 columns,
   `end subroutine Name` written out, one module per file, no commented-out code.
9. Random numbers are seeded through `RandSeedFromInput`.
10. The code runs on one MPI process (more are refused); do not add MPI-only code paths.

## Validation that a pull request must show

- **Old behaviour unchanged:** with the new key off, the regression tests pass and outputs are identical to the
  previous binary (`tests/regression/run_examples.sh`; `model_survey.py` for the Hamiltonian of every model).
- **New behaviour correct:** at least one known-answer test (an analytic limit, a second implementation, or an
  exact diagonalisation), with the numbers in the pull request.
- Every new key gets a case in `tests/regression/model_cases.py`; an intended change of a model is recorded with
  `model_survey.py --update-reference` and explained.
- Build with GNU Fortran (`make.sys.example`) and, when possible, the checked build
  (`tests/regression/config/gfortran.debug.make.sys`). Say which builds and tests were actually run.
- Keep the pull request text short: what changed, why, and one table of the known-answer test.

## Where things are

| Path | Content |
| --- | --- |
| `lanczosKuboCode/Src/` | Fortran sources (`ham.F90` Hamiltonian, `neigh.F90` neighbours, `atoms.F90` geometry, `calc.F90` dispatch, `diag.F90` diagonalisation and TAPW, `kubo*.F90` recursion) |
| `lanczosKuboCode/Src/MIO/` | input, output, memory and timer library |
| `examples/` | supported calculations with reference data |
| `tests/regression/` | regression suite and model survey |
| `docs/user-guide/input-keys.md` | every input key (generated by `tools/input/list_input_keys.py`) |
| `docs/development/` | conventions, validation report, functionality status |
